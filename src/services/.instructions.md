# Services Module — Instructions

## Purpose

Orchestration layer that bridges interface/entry points with domain logic (analysis, forecast, ingestion, admin). Each service manages the lifecycle: interface init → data gathering → domain execution → result persistence → cleanup.

## File Inventory

| File | Class | Role |
|------|-------|------|
| `service.py` | `Service` (abstract) | Base class + `init_service()` factory |
| `analysis_service.py` | `AnalysisService` | Iterates analysis configs, runs each analysis pipeline |
| `forecast_service.py` | `ForecastService` | Manages forecast lifecycle incl. model load/save |
| `ingestion_service.py` | `IngestionService` | Orchestrates data ingestion from file/API to DB |
| `admin_service.py` | `AdminService` | Runs maintenance/admin tasks |

## Class Hierarchy

```
Service (abstract)
├── AnalysisService
├── ForecastService
├── IngestionService
└── AdminService
```

## Key Contracts

### Service Base

- `__init__(name, output_dir, interfaces)` — initializes input/output/mlflow interfaces via `init_interface()`.
- `run()` — abstract, implemented by each subclass.
- `close_service()` — closes all interfaces.

### Factory: `init_service(config) → Service`

- Reads `config["name"]` to dispatch.
- Valid names are in `SERVICES = {"analysis", "forecast", "ingestion", "admin"}`.
- Raises `Exception` if service name is unknown.

## Conventions

- Services receive their full config section from the JSON file (`config['services'][service_name]`).
- Each service iterates over a list of task configs (e.g., `self.forecasts_list`, `self.analysis_list`).
- Output directories are created per-task with an `{id}_{name}` pattern.
- `full_custom_mode` flag allows tasks to manage their own data loading instead of the service layer.

## Refactoring Considerations

- **Duplicate boilerplate**: `AnalysisService.run()` and `ForecastService.run()` share a near-identical loop pattern (iterate configs, check full_custom_mode, fetch data, load/check/run/save). Consider extracting a generic pipeline runner.
- **Interface coupling**: Services directly call `self.input_interface.get_data()` and `self.mlflow_interface.get_model()` — consider a mediator or unit-of-work to decouple.
