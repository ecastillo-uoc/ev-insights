# Forecast Module — Instructions

## Purpose

Core forecasting engine implementing the **Strategy pattern** for pluggable data-preparation and ML-model logic.  Supports training and prediction for session-level and station-level targets using LightGBM, XGBoost, LSTM, Transformer, Hybrid, and Hussain-variant models.

The module provides **two execution paths**:

1. **Service path** — Framework lifecycle managed by `ForecastService` → `init_forecast()` → `GenericForecast.run()`.
2. **Direct pipeline path** — TFM experiments call `pipeline.run_forecast_pipeline()` directly, bypassing the service/interface layers.

## Strategy Interfaces

### PredictionTargetStrategy (data side)

```python
feature_engineering(df, custom_params) → (df, feature_columns, target_columns)
check_data(df) → df
```

**Implementations**: `SessionDataStrategy`, `StationChargesDataStrategy`, `StationEnergyDataStrategy`

### ModelStrategy (ML side)

```python
train(df, feature_columns, target_column, dataset_names, model_name_prefix) → dict
predict(df, feature_columns, target_column, model_objects, context_date, dataset_names, submode) → dict
```

**Implementations**: `LightGBMModelStrategy`, `XGBoostModelStrategy`, `LSTMModelStrategy`, `TransformerModelStrategy`, `HussainTransformerModelStrategy`, `HybridTransformerLSTMModelStrategy`, `HussainHybridModelStrategy`

### Keras Template Method (`base_keras.py`)

`_KerasModelStrategy` is an abstract base shared by all neural strategies.
It defines the train/predict skeleton and delegates model construction to
subclass hooks:

```
_KerasModelStrategy (abstract)
├── LSTMModelStrategy
├── TransformerModelStrategy
├── HussainTransformerModelStrategy
├── HybridTransformerLSTMModelStrategy
└── HussainHybridModelStrategy
```

Key methods:
- `_scale_and_create_sequences()` — MinMaxScaler + sliding-window sequences
- `_filter_train_data()` — optional COVID exclusion + date-range filtering
- `_predict_schedule()` — multi-step recursive (walk-forward) prediction
- `_predict_direct_multistep()` — single-shot multi-output prediction
- `_predict_backtest()` — rolling-origin historical evaluation.
  The first `look_back` rows of the input are consumed as warm-up context;
  predictions, actuals, and dates are returned starting at index `[look_back:]`.
  The pipeline must provide the full test set (never prepend training data).

## Pipeline (`pipeline.py`)

`run_forecast_pipeline()` is the standalone orchestrator used by the TFM
module.  It bypasses the service/interface layers and directly:

1. Fetches data via `src.data.data_fetcher.fetch_daily_energy_for_forecast()`
2. Applies feature engineering via `src.forecast.feature_engineering`
3. Instantiates the model strategy via `_STRATEGY_REGISTRY` + `_make_strategy()`
4. Calls `strategy.train()` then `strategy.predict()`
5. Computes metrics (sMAPE, RMSE, MAE, MSE, R²)

The first `look_back` rows of the test set serve as warm-up context for the
backtest.  Predictions, actuals, and dates returned by `_predict_backtest`
correspond to `test[look_back:]`.  Metrics and plots reflect only this valid
evaluation window.
6. Generates plots via `src.analysis.forecast_plots`
7. Optionally logs to MLflow

The `_STRATEGY_REGISTRY` dict maps model-type strings to strategy classes:

```python
_STRATEGY_REGISTRY = {
    "lstm": LSTMModelStrategy,
    "transformer": TransformerModelStrategy,
    "hussain_lstm": LSTMModelStrategy,
    "hussain_transformer": HussainTransformerModelStrategy,
    "hussain_hybrid": HussainHybridModelStrategy,
    "hybrid": HybridTransformerLSTMModelStrategy,
    "lightgbm": LightGBMModelStrategy,
    "xgboost": XGBoostModelStrategy,
}
```

## Feature Engineering (`feature_engineering.py`)

Three orthogonal capabilities controlled by boolean flags in `strategy_params`:

| Flag | Feature | Functions |
|------|---------|-----------|
| `use_calendar_features` | Day-of-week, month, sin/cos day-of-year, business day | `compute_calendar_row()`, `add_calendar_features()` |
| (always for tree models) | Lag + rolling-window features | `add_tree_lag_features()` |
| `use_log_transform` / `use_differencing` | Target transforms with invertible state | `TargetTransformState`, `apply_forward_transforms()`, `apply_inverse_transforms()` |

## Registry System

### Model Registry (`model_registry.py`)

- `ModelStrategyType` enum: `LIGHTGBM`, `XGBOOST`, `LSTM`, `TRANSFORMER`, `HUSSAIN_TRANSFORMER`, `HYBRID_TRANSFORMER_LSTM`
- `MODEL_STRATEGY_REGISTRY`: maps enum → `ModelStrategyInfo(name, display_name, description, strategy_class, default_params)`
- Factory: `get_model_strategy(strategy_type) → ModelStrategy`

### Prediction Target Registry (`prediction_target_registry.py`)

- `PredictionTarget` enum: `SESSION_ENERGY`, `SESSION_DURATION`, `STATION_CHARGES`, `STATION_ENERGY`
- `PREDICTION_TARGET_REGISTRY`: maps enum → `PredictionTargetInfo(name, display_name, description, strategy_class, default_params, init_params)`
- Factory: `get_prediction_target_strategy(target_type) → PredictionTargetStrategy`
- Includes default field lists and `custom_params` per target type.

## Forecast Factory (`init_forecast`)

1. Reads `config["name"]` (e.g., `"lightgbm_station_energy"`).
2. If `prediction_target` and/or `model_strategy` keys exist in config, uses registries to build strategies dynamically.
3. Otherwise, falls back to importing a pre-defined class from `forecast_definitions.py` by name.
4. Injects strategies into `GenericForecast.__init__()`.

## Execution Flows

### Service Path (Framework / UI)

```
ForecastService.run()
  → init_forecast(config)          # factory
  → forecast.load_data(df)         # from interface
  → forecast.check_data()          # via data_strategy
  → forecast.feature_engineering() # via data_strategy
  → forecast.run()                 # delegates to train() or predict()
      → model_strategy.train()  OR  model_strategy.predict()
```

### Direct Pipeline Path (TFM Experiments)

```
tfm_forecast.execute_*(datasets, horizons)
  → get_dataset_config(ds)
  → run_forecast_pipeline([ds], params, split_date_str, model_type)
      → fetch_daily_energy_for_forecast(ds)       # src.data.data_fetcher
      → feature_engineering.add_calendar_features() # if enabled
      → _make_strategy(model_type).train()
      → _make_strategy(model_type).predict()
      → compute metrics + generate plots + MLflow
```

## Model Persistence

- `save_model(name, results, models_dir, algo)` — dispatches on model type to save `.ubj` (boosting) or `.keras` + `.pkl` (neural).
- `load_model(algo, model_name, models_dir)` — auto-detects format; tries Keras first, then `.ubj` with LightGBM/XGBoost fallback.
- `list_models(models_dir)` — scans directory for available model names.

## Conventions

- Strategy classes are defined in individual files under `strategies/` and re-exported via `strategies/__init__.py`.
- Class names for `forecast_definitions.py` use **`snake_case`** to match module filenames for dynamic import.
- `custom_params` are passed on `df.attrs` keyed by strategy name (see `_STRATEGY_ATTRS_KEY` in `generic_forecast.py`).
- Neural strategies share a common base in `base_keras.py` — new Keras architectures should subclass `_KerasModelStrategy`.

## Adding a New Model Strategy

1. Create `strategies/<name>_strategy.py` implementing `ModelStrategy` (or subclassing `_KerasModelStrategy`).
2. Re-export in `strategies/__init__.py` and add to `__all__`.
3. Register in `model_registry.py` (`ModelStrategyType` enum + `MODEL_STRATEGY_REGISTRY`).
4. Add model persistence support in `model_persistence.py` if the file format differs.
5. Add the model-type string to `_STRATEGY_REGISTRY` in `pipeline.py` for TFM usage.

## Known Issues

- **`_resolve_model_strategy()`** in `GenericForecast` uses `isinstance` checks to auto-switch strategies at predict time — fragile coupling.  Better to persist the strategy type alongside the model.
- **`forecast_definitions.py` classes are boilerplate**: Each is only 4 lines.  Consider generating them dynamically from the registry or removing them in favour of config-only instantiation.
- **Deprecated files**: `helpers.py` and `split_dataset.py` are unused but kept for reference.
