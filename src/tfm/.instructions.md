# TFM Module — Instructions

## Purpose

Master's thesis (TFM) specific code for experimental forecasting, hyperparameter optimization, and custom visualizations. This module sits outside the main framework pipeline and is used for research experiments.

## File Inventory

| File | Role |
|------|------|
| `tfm_forecast.py` | End-to-end forecast pipeline for thesis experiments |
| `tfm_data_fetcher.py` | Data retrieval functions (daily energy per station via SQLAlchemy) |
| `tfm_plots.py` | Custom plotting functions for thesis figures |
| `tfm_constants.py` | Constants: `COVID_START`, `COVID_END` dates |
| `param_optimization.py` | Optuna objectives for LSTM and Transformer hyperparameter search |

## Key Functions

### `tfm_forecast.py`

- `run_forecast_pipeline()` — Main pipeline: fetches data per dataset, runs multi-lag predictions across multiple models.
- `plot_train_test_split(train, test, dataset_name, test_size)` — Visualizes data split.
- `plot_test_vs_predict(test, predictions, dataset_name, model_name, test_size)` — Compares actuals vs predictions.

### `tfm_data_fetcher.py`

- `fetch_daily_energy_for_forecast(dataset)` — Retrieves daily aggregated energy time series per station.
- Uses SQLAlchemy `create_engine()` directly (not via the Interface layer).

### `param_optimization.py`

- `objective_lstm(trial)` — Optuna objective for LSTM hyperparameter tuning.
- `objective_transformer(trial)` — Optuna objective for Transformer hyperparameter tuning.

## Models Used

- `LSTMModelStrategy`
- `TransformerModelStrategy`
- `LightGBMModelStrategy`
- `XGBoostModelStrategy`
- `HybridTransformerLSTMModelStrategy`

## Conventions

- Imports model strategies directly from `forecast_implementations.py`.
- Uses `model_persistence.save_model()` / `load_model()` for file-based persistence.
- ANSI color highlighting via `Colors` from `src.utils.console`.
- Output plots go to `output_plots/` at project root.
- Uses `matplotlib` for plotting (not Plotly).
- Logging via `logging.basicConfig()` (standalone, not the framework Logger).

## Refactoring Considerations

- **Direct SQLAlchemy usage**: `tfm_data_fetcher.py` creates its own DB engine instead of using the `PostgreSql` interface. Refactor to use the interface for consistency and credential management.
- **Hardcoded paths**: `output_plots/` and model paths may be relative to working directory. Use config or constants.
- **Standalone logging**: Uses `logging.basicConfig()` instead of `src.utils.logger.Logger`. Integrate with the framework logger.
- **`sys.path.append` manipulation**: Fragile path setup. Ensure proper package installation or use relative imports.
- **Code overlap with `forecast/`**: Several functions duplicate logic already in model strategies. After experiments stabilize, consolidate reusable parts back into the main `forecast/` module.
- **COVID date filtering**: `COVID_START`/`COVID_END` constants are used to exclude data — document the rationale and make configurable.
